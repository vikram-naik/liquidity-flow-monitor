# ML Guard: Iterative Training & Promotion Workflow

This document establishes the institutionalized process for periodically retraining the XGBoost ML Guard, evaluating its performance across both the Machine Learning domain and the Quant (Backtesting) domain, and promoting new models to production.

## 1. Rationale and Cadence
Financial markets evolve. The structural conditions that define a "Good" vs "Bad" setup shift over time. To prevent model decay, the XGBoost model should be iteratively retrained on fresh historical data.
**Recommended Cadence:** Monthly or after a significant market regime change.

## 2. Artifact Naming Convention
To ensure reproducibility and easy rollbacks, all data and model artifacts MUST be versioned with a timestamp (`YYYYMMDD`).
*   **Dataset:** `output/ml/dataset_trade_YYYYMMDD.csv`
*   **Model Binary:** `src/trading/signals/savgol_cts/models/model_xgb_YYYYMMDD.joblib`

*Note: The model binary is explicitly checked into the `src/` tree to ensure Git tracks the exact weights used for backtesting at any given commit.*

## 3. The Iterative Process

### Step 1: Extract Real-World Trade Features
Instead of using theoretical Oracle points, the system trains on actual historical trades generated by the `SavgolCTS` engine. This captures the exact indicator state at the moment a signal fires, paired with the actual PnL outcome of the system's trailing exits and hard stops.

Run the extraction script:
```bash
./venv/bin/python scripts/extract_features_from_trades.py
```
*Output:* `output/ml/dataset_trade_<DATE>.csv`

### Step 2: Train the XGBoost Model
The training script loads the versioned dataset, splits it (80/20 stratified), applies a cost-sensitive class weight (penalizing false positives/bad trades), and trains the XGBoost classifier.

Run the training script:
```bash
./venv/bin/python scripts/train_ml_guard.py --dataset output/ml/dataset_trade_<DATE>.csv
```
*Output:* `src/trading/signals/savgol_cts/models/model_xgb_<DATE>.joblib`

*Review the ML Metrics:* The script outputs a `Classification Report`. Ensure the model has successfully learned to identify the minority class ("Good Trades" - Class 1) without excessive false positives.

### Step 3: Quant Domain Validation
A model that performs well in `scikit-learn` might fail in a path-dependent backtest. You MUST validate the new model's efficacy against the actual trading simulator.

1.  **Update the Active Model:** Edit `src/trading/signals/savgol_cts/ml_guard.py` (or the relevant config) to point to the newly generated `model_xgb_<DATE>.joblib`.
2.  **Threshold Analysis:** Run the threshold study to see how the new model scores out-of-sample trades:
    ```bash
    ./venv/bin/python scripts/analyze_score_thresholds.py
    ```
    Ensure that at the target threshold (e.g., `80.0`), the system achieves a strong Win Rate (>60%) and high Average PnL, while successfully filtering out catastrophic drawdowns.
3.  **Full System Walk-Forward:** Run the exhaustive system backtest to ensure the new model plays nicely with the rest of the portfolio and doesn't choke out overall volume:
    ```bash
    ./venv/bin/python scripts/walk_forward.py --watchlist "NIFTY 50"
    ```

### Step 4: Promotion & Rollback
Once the Quant Validation is successful:
1.  Commit the new `model_xgb_<DATE>.joblib` binary to the repository.
2.  Commit the updated pointer in `ml_guard.py`.
3.  Document the new baseline metrics in the PR/Commit message.

**Rollback:** If a newly promoted model begins underperforming in live trading, simply revert the model pointer in `ml_guard.py` to the previous `YYYYMMDD.joblib` artifact and flush the cache.
